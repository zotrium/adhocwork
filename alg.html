1. The simplest mental model

🛡️

Data Suppression

Question answered: “Is it safe and statistically valid to show this number?”

If the sample is too small or too few firms contributed, hide the statistic instead of showing a misleading or confidential value.

⚖️

Data Dominance

Question answered: “Is one firm too large in this market sample?”

If one company contributes more than the configured percentage threshold, scale it back so it does not drive the market result.

🎯

Best Match

Question answered: “What is the best available market benchmark for this incumbent?”

Try the most specific job/scope first; if unavailable, walk down a configured fallback ladder until a usable market value is found.

Important ordering: the document says STINC is evaluated before suppression, and STINC pre-empts suppression. In plain English: first decide if the statistic is statistically invalid; only after that do confidentiality suppression checks apply.
Algorithm 1

2. Data Suppression

Data Suppression is the system’s “do not show this statistic” mechanism. It exists for two related but different reasons:

STINC: statistically invalid calculation

A STINC happens when there are not enough data points — incumbents — for a calculation to be statistically valid.

Example: if the statistic requires enough market observations to calculate a percentile reliably, but the market sample is too thin, the system should mark the value as STINC rather than outputting a number.

Confidentiality suppression

Suppression also happens when too few companies contributed data, because exposing the value could reveal or imply a participating firm’s compensation information.

Example: if only a small number of firms provided data for a job, the system may hide the median even if there are several incumbents.

Typical decision flow

Input samplejob, scope, element, statistic
Check STINCenough incumbents?
Check confidentialityenough firms?
Show statisticif all rules pass
Return reasonSTINC or suppressed

Algorithm 2

3. Data Dominance / Balancing

Data Dominance prevents one company from dominating the market sample. If a firm contributes more than the allowed threshold — for example 25% of incumbents for a position — its data is scaled back or balanced so the firm does not significantly drive market compensation levels.

Plain-English example: suppose a job has 40 market incumbents and Company A contributes 18. If the dominance cap is 25%, Company A should not contribute more than 10 of the 40. The balancing process reduces Company A’s included incumbents while trying to preserve the shape of Company A’s pay distribution.

Dominance loop

  1. Group incumbents by market cut: job, scope, pay element, and any other relevant cut.
  2. Count incumbents by firm.
  3. Compute each firm’s share of the sample.
  4. If any firm exceeds the configured threshold, reduce that firm to the threshold.
  5. Recalculate shares, because reducing one firm can make another firm exceed the threshold.
  6. Repeat until no firm exceeds the threshold.
Why repeat? The source principles state that after reducing company X to threshold, company Y may now exceed the threshold. The algorithm should continue until no company is above the cap.

Sampling method

4. Equal Spread sampling

Equal Spread is the first/default sampling method described for Fusion. It is not random. The specification explicitly requires repeatable results: running the same raw sample again should exclude the same incumbents.

What it tries to preserve

The source document says the shape of the company’s data should remain as close as possible to the original. That means if the firm’s salaries range from low to high, the removed incumbents should be spread across the range rather than all coming from the bottom or top.

How it becomes repeatable

Incumbents are ranked by one compensation element — for example base salary. If there is a tie, the system uses Employee ID as a secondary sort key because it is constant and unique to the employee.

Beginner-friendly explanation

Imagine a firm has 10 employees sorted from lowest to highest salary. We need to keep 5. Equal Spread does not keep the first 5 or last 5. It keeps roughly every other person, so the retained sample still represents the low, middle, and high parts of that firm’s distribution.

Input:  01 02 03 04 05 06 07 08 09 10
Keep:      02    04    06    08    10
Remove: 01    03    05    07    09

The exact positions depend on the keep/remove ratio and the documented rounding rule.

Implementation-shaped pseudocode

for each firm in market_cut:
    sort firm incumbents by sampling_compensation_element asc, employee_id asc
    original_count = count(firm incumbents)
    target_count = allowed_count_after_dominance_cap
    sampling_ratio = target_count / original_count

    last_credit = 0
    for k from 1 to original_count:
        credit = k * sampling_ratio
        # Source rule: handle .5 by leaning toward the median.
        # Practical implementation: centralize this rounding behavior in one tested function.
        if rounded_credit_changed(last_credit, credit, target_count):
            keep incumbent k
        else:
            remove incumbent k
        last_credit = credit
Hinting: The source includes worked examples for “take first” and “take last” hints. Engineer-friendly interpretation: some incumbents are pre-marked to be removed first or retained last, and the Equal Spread algorithm is then applied to the remaining eligible group when needed.
Hint situationBehavior to implement

5. Best Match algorithm

Best Match chooses an incumbent’s best benchmark for comparison. The source definition says it should be closest to the incumbent’s source job code, based on report setup parameters and priority orders assigned to primary scopes and roll-ups. The objective is to ensure each incumbent has a market value to compare against.

The fallback ladder

1
Source Job Code + Primary Scope
Most specific. Example: exact job plus geography or MBA class scope.
Try first
2
Source Job Code only
If scoped market value is unavailable, try the job without the scope.
Fallback
3
Roll-up Job Code + Primary Scope
If the exact job is too thin, try a configured roll-up while keeping scope.
Fallback
4
Roll-up Job Code only
Broadest automatic match in the documented list.
Last resort
Primary vs secondary scopes: Primary scopes are part of a position’s job description and participate in Best Match. Secondary scopes are alternate views and are not included in Best Match logic.

Best Match depends on

  • Best Match logic selected during report setup.
  • Dataset selection, including incumbents defined by job list and peer list.
  • Compensation element used to determine Best Match. The document says Total Compensation is typically used, with Current Year Salary often used if Total Compensation is unavailable.
  • Market statistic used to determine Best Match. The document says Market Median is typically used.
  • Suppression mode and same-store / year-on-year analysis settings.
  • Priority order of primary scopes and roll-ups.
Optional behavior: extrapolating missing quartiles

The source says market median data is required for a position to be considered a Best Match. It also describes an option to model missing quartiles from the median: Low Quartile = 70% of market median, High Quartile = 130% of market median. It notes these factors and percentiles should be configurable by the user.

Manual assignment

The source says users can manually assign a best-match position for incumbents before reports are run. This supports full-population reporting when automatic logic does not assign every incumbent.

6. Engineering checklist

Domain model

  • Represent suppression rules by statistic, sample type, market, and threshold.
  • Store STINC status separately from confidentiality suppression status.
  • Represent dominance threshold as configuration, not a magic number.
  • Track sampling element and tie-breaker explicitly.
  • Store Best Match sequences as ordered reference data.

Test cases

  • STINC pre-empts suppression.
  • Median, quartile, 90th percentile use different thresholds.
  • Dominance balancing repeats until no firm exceeds threshold.
  • Equal Spread is deterministic for same input ordering.
  • Employee ID tie-breaker produces stable ordering.
  • Best Match walks fallback ladder in configured order.
  • Manual Best Match overrides automatic assignment where applicable.

Common pitfalls

PitfallWhy it is riskySafer approach
Using random samplingResults are not repeatable.Use deterministic Equal Spread logic and stable tie-breakers.
Applying suppression before STINCContradicts the documented rule ordering.Evaluate STINC first, then confidentiality suppression.
Only balancing onceAnother firm may exceed the cap after the first reduction.Loop until all firms are within threshold.
Hard-coding Best Match ladderPriority orders can vary by setup and business rules.Store the ladder as configurable ordered reference data.
Moving huge raw samples to the API layerCan be slow and expensive for large market datasets.Run heavy grouping, suppression, dominance, and matching near the data; expose summarized results to the API/dashboard.

7. Suggested implementation shape

For a scalable analytics platform, keep the heavy operations near the data and expose compact, explainable outputs to downstream APIs and dashboards.

Raw incumbent data
  → clean / normalize / currency handling
  → create market cuts by job, scope, element, statistic
  → apply STINC checks
  → apply confidentiality suppression checks
  → apply dominance balancing / weighting
  → calculate statistics
  → determine Best Match for each incumbent
  → publish report-ready dataset with status, reason codes, and lineage
Engineer-friendly output principle: every hidden or chosen value should have a reason code. New engineers should be able to answer: “Why did this statistic disappear?” or “Why was this benchmark selected?” without reverse-engineering the entire pipeline.
